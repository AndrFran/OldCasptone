Infrastructure Provisioning Pipeline — Terraform

Two workflows: terraform.yml runs CI and produces a plan per environment; terraform-deploy.yml is a reusable job called once per environment behind a manual approval gate.

1 · terraform.yml — the pipeline

What to say

  1. Triggers. Any push to main, any PR, or a manual run — but only when something under terraform/** changed, so app-only commits don't burn CI minutes. concurrency cancels the previous run on the same branch.
  2. lint. terraform fmt -check -recursive fails on unformatted HCL; tflint (recommended ruleset) catches unpinned providers, untyped variables and dead declarations. Cheapest job, so it runs first and gates everything else.
  3. validate + test run in parallel — both only need lint. validate checks the config parses and type-checks; test runs the native terraform test suite: naming convention, per-environment fleet size, two rejected-input cases, and inventory contents.
  4. plan is a matrix — one job per environment, each with its own .tfvars. fail-fast: false so a broken prod plan still shows you the dev and staging results. Each job uploads its plan as an artifact, writes it to the job summary, and posts it as a PR comment.
  5. deploy is three calls to the same reusable workflow, chained with needs so dev must finish before staging starts. Skipped entirely on pull requests.

2 · terraform-deploy.yml — the reusable deploy job

What to say

  1. Why reusable. Three environments, one file. Adding a fourth environment is a five-line caller job, not a copy-paste of the whole deploy sequence.
  2. Where the approval lives. environment: ${{ inputs.environment }} is the entire mechanism — GitHub blocks the job before its first step until a required reviewer approves. The gate is repo configuration, not YAML, so reviewers can change without a commit.
  3. The artifact hand-off. The job downloads tfplan-<env>, the exact plan the reviewer looked at, so what was approved and what runs are provably the same commit.
  4. Dry run. Step 5 runs terraform plan, never apply. Nothing is created — the pipeline proves it could deploy.
One-time setup: Settings → Environments → create dev, staging, prod and add required reviewers. That is the whole approval configuration; no workflow change needed.
